### [03:30] Redstone inbound status callback: built, secured, shipped   (branch: develop → main · commits: 1597caa, 41e3bcd)

**Synopsis:** Redstone's reply moved status tracking from blocked-on-them to
blocked-on-us. Chose the auth scheme, built the callback endpoint, hardened it
against its own auth failing, and deployed to production with the token set.

**The decision and why:** auth is a **high-entropy secret in the URL path**.
Travis said "we just need the endpoint where we'll post that data, and we'll
save it to your company profile" — their system stores a URL and nothing else,
so a header secret or HMAC means development on their side, which he quoted in
weeks. A path token costs them zero. The judgement is that **the binding
constraint is their team's capacity**, so every requirement we impose is delay
on our own critical path.

Consequently the token is **not** treated as sufficient. A leaked token can
only do what was already going to happen: advance an existing dispatch, forward
only via `applyDispatchTransition`, for a vendor actually flagged Redstone,
idempotently. Worst case is "an order is marked shipped early" — bad, bounded,
detectable, and no money moves because capture happens at customer approval.

**What worked:**
- Reading their spec properly instead of guessing. §4.4 gives their exact
  status vocabulary AND says "We can map the status names that your platform is
  expecting", so the email asks them to send ours; the endpoint accepts BOTH
  vocabularies so the integration survives whichever they pick. §5 defines the
  response envelope `{"fail":false,"msg":"ok"}` — answering in their vocabulary
  stops their client retrying against a 200 it does not recognise.
- **Found a likely cause of the 500 in their own docs:** their validation error
  list includes "data may not contain credentials in the URL", and our signed
  Supabase links carry the signature as `?token=`. That is now the lead item in
  the reply, with an offer to switch to path-style URLs. Far stronger than the
  vague question the first draft had.
- `Completed Production` deliberately maps to `in_production`, NOT `shipped` —
  printed is not mailed, and `shipped` is what emails the customer.

**The schema trap avoided:** `admin_audit_log.actor_id` is
`NOT NULL REFERENCES auth.users(id)`. A vendor callback has no user, so a
synthetic id would fail the FK and be **swallowed by logAdminAction's
try/catch** — losing the audit trail on the one path with no human behind it,
the same silent-failure class as `payment_transactions` and
`orders.updated_at`. Hence `vendor_status_callbacks`, which also carries the
idempotency key and stores raw bodies (including unparseable ones).
`updateDispatchStatus` now takes `actorId: string | null`.

**What did NOT work / corrections:**
- I told Rob to send the callback URL by something other than plain email. That
  was reflexive security theatre: Redstone must store the URL in their system
  regardless, and the endpoint was explicitly designed assuming the token
  leaks. He pushed back and was right. Corrected the note in the draft. **The
  API key is a real credential; the webhook token is a scoped capability — do
  not conflate them.**
- I then told him the Vercel CLI was unavailable, trusting the SessionStart
  hook's "IMPORTANT: The Vercel CLI is not installed". **It is installed**
  (54.14.1, authenticated as rspeciale0519) and set the env var fine. The hook
  is wrong; recorded as `memory:project-vercel-cli-is-installed`, since the
  Vercel MCP has no env tool and the CLI is the only way to manage them.
- Near-miss: created `.env.local.bak-<ts>` before appending the token, and
  `.gitignore` only had `.env.local.bak` **exactly**, so the timestamped backup
  was NOT ignored. Caught it with `git check-ignore` before staging; removed the
  backup and widened the pattern to `.env.local.bak*`.

**Artifacts:** `app/api/webhooks/redstone/[token]/route.ts`,

### [17:45] Truthfulness audit of the Redstone reply; two real bugs found   (branch: develop → main · commits: 42f7c9f, efccb58, d14e3dc)

**Synopsis:** Owner asked "make sure this email is truthful", then twice asked
"are you 100% sure it is ready". Both challenges were correct: auditing the
claims found four false statements, and properly verifying the endpoint found a
silent-drop bug. Email sent after fixing all of it.

**What worked — auditing claims against sources rather than memory:**

Four statements in the draft were not true:
1. *"I have since changed our side to keep raw responses"* — aspirational.
   `submitRedstoneOrder` still discarded bodies. Made it true: it now returns
   the last response verbatim via a pure `buildRawResponse` that redacts our
   key from body AND headers (the key rides in the query string, so an echoed
   URL would leak it into anything we persist) and bounds the body, since their
   rejections are unbounded HTML pages. 7 tests.
2. *"Every failure came back as an HTML 500"* — false. createOrder attempts
   returned HTML 500; after ~8 posts responses switched to JSON
   `{"fail":true,"msg":"Where did you come from?"}`. Split into two facts, and
   the rate-guard detail handed to Travis as a place to grep.
3. **The boolean-vs-string theory was REMOVED.** Extracting §8 of their spec
   showed their own JSON example uses `"api_test": true` (boolean) and
   `"qty_est": "1000"` (string) — exactly our typing. Their own example would
   fail if that were the bug. Sending a hypothesis I held evidence *against*
   would have wasted his time.
4. *"We can take tracking links at the same endpoint"* — false. The handler
   requires a recognised status, so a tracking-only post is rejected. Said so
   plainly and offered to build one.

Bonus find in the same extraction: **their spec's JSON example IS wrapped in
`{"Order": …}`**, contradicting Travis's "do not wrap". Flagged to him, noting
we follow his instruction but the deployed endpoint may still follow the doc.

**What did NOT work — and why the second "are you sure" mattered:**

I had verified only that a **wrong** token returns 401. I never verified the
**real** token authenticates. Those are different tests: had `printf` appended a
newline or Vercel stored whitespace, the real token would also 401 and every
post Travis sent would bounce. Testing it live (400 "Missing order id" on an
empty body = auth passed; 200 "Unknown order id" on a fake order) proved it
works — and reading back the audit rows exposed a genuine bug:

**The unmatched path let a failed record claim the dedupe key.** Trace: Redstone
posts a status a moment before the order row is visible → we write `unmatched`
holding `"<order>:<status>"` → every legitimate retry then collides with
`uq_vendor_status_callbacks_dedupe`, is treated as an already-processed replay,
acked, and **silently dropped forever**. Same class as `payment_transactions`
and `orders.updated_at`. Fixed: only a record of successful processing may claim
the key. Verified live — two identical retries now both record with
`dedupe_key: null`.

**Rule earned:** "wrong credential is rejected" does NOT verify "right
credential is accepted". Test both directions, always.

**Also:** committed to `main` twice by accident after `git checkout main` for
the Vercel CLI deploy, both caught by the "Everything up-to-date" push output,
both cherry-picked to develop and `main` reset. Second time is a pattern — after
