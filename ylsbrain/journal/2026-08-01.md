# Journal — 2026-08-01

### [12:40] Money-moment confirmations + Redstone API dispatch (Phase 1)   (branch: feature/vendor-fulfillment · commits: fb8e19e, a0f7d56)

**Synopsis:** Owner asked whether the wizard confirms design approval before
payment and again before submitting, then had me fix what I found and start the
Redstone API integration. Two defects were real: the review step displayed four
approval checkboxes while `validateCurrentStep` gated on only two (so a customer
could leave "non-refundable" unchecked, see the red "complete all approval
items" banner, and continue anyway); and `Approve & capture payment` — the only
irreversible action in the customer flow — fired on a single tap while the
harmless `Reject proof` beside it had a `window.confirm`. Collapsed the four
boxes to two enforced ones (owner-specified wording: "…and I understand that all
orders are non-refundable"), added `ConfirmActionDialog`, and put it in front of
both money moments. Then built the outbound Redstone leg and probed the live API
with the owner-authorized test order.

**What worked:** Probing the vendor API before writing a line of integration
code. Evidence: `dev-docs/api-redstone.md` turned out to be **fabricated** —
`api.`/`test-api.redstonemail.com` present no valid TLS cert, the documented
endpoints (`postNewOrder`, `postJSONorder`, `uploadArtwork`, `getBatchStatus`)
are not the real one (`createOrder`), it describes the key as "32-char
alphanumeric" when the real key is a 36-char UUID, and it lists `(555) 123-MAIL`
plus RFC1918 ranges as Redstone's webhook sources. Building from it would have
produced code that could never work. The real spec is the owner-supplied PDF
`docs/temp/vendors/redstone/rsm_api_specs_pre-r631-1.pdf` (extracted with pypdf
installed to the scratchpad, not globally).

Key auth was proven by contrast, not assumption: no key and a bogus UUID both
return `{"fail":true,"msg":"Where did you come from?"}`, while the real key got
past that gate into the handler. Two live-verified quirks are now encoded in
`classifyRedstoneResponse` and covered by tests: **HTTP 200 does not mean
success** (failures arrive as `200` + `{"fail":true,…}`), and a malformed
payload returns an **HTML 500**, not the `422` JSON the spec describes — the PDF
is labelled *pre-*r631-1 and the deployed build predates that table. Because a
rejected payload cannot be self-diagnosed, the client retries only
throttling/maintenance/network and never re-sends a rejected body.

Gates: `typecheck:full` 0 errors, **258 tests passing** (233 → 258, +25 Redstone
core), `npm run build` exit 0.

**What did NOT work:** The authorized `api_test:true` order never succeeded.
`createOrder` returned the same opaque HTML 500 for **four** well-formed shapes
— flat, `{"Order":{…}}`-wrapped, with `seeds`, and form-encoded — so the
spec's own wrapper ambiguity (§8 JSON example vs Appendix B) is still
unresolved. Then, after ~8 posts, **all three intake endpoints began rejecting
the valid key** with "Where did you come from?", the same response previously
seen only for a missing/bogus key. Almost certainly a rate or abuse guard.
**Stopped probing** rather than risk a harder block. Inference (not confirmed):
spec §4.1/§4.2 say Redstone generates the endpoint per customer after reviewing
your data — our account is likely not provisioned, which would mean the outbound
half cannot be finished unilaterally either, and contacting Redstone is the
critical path in **both** directions, not just for webhooks.

Also unverified: no browser pass on the two new dialogs (Chrome CDP was wedged
at the end of the previous session; not retried here). Local Supabase is
`127.0.0.1`, so no signed URL we generate is reachable by Redstone — the live
test used a public synthetic CSV (FSU `addresses.csv`), never customer data.
